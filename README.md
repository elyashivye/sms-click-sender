# SMS Click Sender

שליחת SMS **או WhatsApp** מותאמים אישית לרשימת אנשי קשר, דרך טלפון אנדרואיד
המחובר בכבל USB - **ישירות מהדפדפן**, בלי Python, בלי `adb` מותקן מראש.
שלושה חלקים באותו פרויקט:

1. **אתר** - שליחה חד-פעמית בלחיצה, מכל דפדפן Chromium. אין לו תלות
   בשרת בכלל, אפשר לארח כקבצים סטטיים בכל מקום (כולל הוסטינגר).
2. **תוכנה להורדה** (Electron) - אותה חוויית שליחה, ובנוסף **תזמונים
   ותזכורות** שרצים ברקע גם כשהחלון סגור.
3. **שרת קטן** (Node.js) - נחוץ **רק** לתזמונים. הוא לא נוגע בטלפון בעצמו
   ולא מחזיק רשימות אנשי קשר/תוכן הודעות - רק "מתי" לתזמון, לא "מה".

## איך זה עובד

הדפדפן (Chrome/Edge) מדבר עם הטלפון ישירות דרך **WebUSB**, באמצעות מימוש
מלא של פרוטוקול ADB ב-JavaScript (ספריות [Tango ADB](https://github.com/yume-chan/ya-webadb)).
לכל איש קשר, המערכת פותחת את מסך כתיבת ה-SMS בטלפון עם המספר וההודעה כבר
ממולאים, מאתרת אוטומטית את כפתור "שלח" על המסך (על ידי קריאת מבנה המסך
בזמן אמת - לא קואורדינטות קבועות), ומדמה הקשה עליו.

**בשימוש הרגיל (שליחה חד-פעמית), שום דבר לא נשלח לשום שרת** - הקובץ,
ההודעה, והתקשורת עם הטלפון, כולם קורים מקומית בטאב הדפדפן/בתוכנת ה-Desktop.

**אם מגדירים תזמון** (רק בתוכנה להורדה): השרת הקטן שומר מתי להריץ ("כל
יום ב-9:00" למשל) ובודק את זה כשמישהו שואל אותו - הוא לא "מתעורר לבד",
כך שהוא מתאים גם לאירוח משותף פשוט. התוכנה להורדה, כל כמה דקות, שואלת
את השרת "יש לי עבודה?" - וכשהתשובה כן, **היא** (לא השרת) מריצה בפועל את
השליחה מהתוכן שנשמר אצלה מקומית, ומדווחת לשרת שסיימה. כלומר רשימת אנשי
הקשר ותוכן ההודעה אף פעם לא עוזבים את המחשב שלך.

## דרישות

- דפדפן מבוסס **Chromium בלבד**: Chrome, Edge או Opera. **לא** Firefox
  ו**לא** Safari - הם לא תומכים ב-WebUSB.
- **HTTPS** (או `localhost`) - WebUSB לא עובד ב-http:// רגיל מכתובת מרוחקת.
- טלפון אנדרואיד עם **ניפוי USB (USB Debugging)** מופעל (הגדרות → אודות
  הטלפון → הקש 7 פעמים על "מספר build" כדי לחשוף "אפשרויות למפתחים", ואז
  הפעל שם "ניפוי USB")
- כבל USB בין הטלפון למחשב
- Node.js 18+ רק כדי **לבנות**/**לפתח** את הפרויקט (למשתמש הסופי באתר לא
  צריך Node בכלל - זה HTML/JS רגיל)

## הרצה מקומית לפיתוח

```
npm install
npm run dev
```
ופותחים את הכתובת שמודפסת (בד"כ http://localhost:5173).

## פריסה כאתר (כולל הוסטינגר)

```
npm run build
```
זה יוצר תיקיית `dist/` עם קבצים סטטיים בלבד (HTML/CSS/JS) - **בלי** תלות
בשרת מכל סוג. מעלים את תוכן `dist/` לכל שירות אחסון סטטי (הוסטינגר, GitHub
Pages, Netlify, Cloudflare Pages וכו').

חשוב: השירות חייב להגיש את הקבצים דרך **HTTPS** (רוב שירותי האחסון,
כולל הוסטינגר, נותנים SSL חינמי כברירת מחדל). כל מי שנכנס לאתר עם Chrome
ומחבר טלפון **למחשב שלו** יכול להשתמש בו - אין צורך בהרשאות/סיסמה, כי
אין שרת שמחזיק מידע או ניגש לטלפון של אף אחד מרחוק.

## בניית תוכנה להורדה (Desktop, Electron)

אותו קוד בדיוק, עטוף בחלון עצמאי (Electron - אותה טכנולוגיה שעליה בנויים
Slack/Discord/VS Code) כדי שאפשר יהיה להוריד קובץ, להתקין, ולהשתמש בלי
לפתוח דפדפן/אתר בכלל.

פיתוח/בדיקה:
```
npm run electron:dev
```

בניית קובץ התקנה (Windows/.exe, Mac/.dmg, Linux/.AppImage - כל אחד נבנה
על המערכת המתאימה לו):
```
npm run electron:build
```
התוצאה תופיע בתיקיית `release/`.

### הורדה מהאתר

עמוד "הורדת התוכנה" באתר (מוסתר בתוך התוכנה להורדה עצמה - רלוונטי רק
באתר בדפדפן) מקשר ישירות לשלושת קבצי ההתקנה. הקישורים **קבועים** ולא
משתנים בין גרסאות (`.../releases/latest/download/<שם-קובץ>` - כתובת
סטנדרטית של גיטהאב שתמיד מצביעה לגרסה העדכנית), בזכות `artifactName`
קבוע לכל פלטפורמה בהגדרת ה-`build` שב-`package.json`.

הבנייה עצמה קורית אוטומטית: `.github/workflows/build-desktop-app.yml`
בונה את שלושת הקבצים (על ריצת Windows/Mac/Linux נפרדת בגיטהאב Actions,
כי לכל מערכת הפעלה יש לבנות את ההתקנה שלה) בכל פעם שדוחפים לענף הראשי,
ומפרסם אותם כ"latest" release קבוע בגיטהאב - בלי שום פעולה ידנית. הקבצים
לא חתומים דיגיטלית (זה עולה כסף), אז בהרצה ראשונה תופיע אזהרת "מפרסם לא
מזוהה" - זה מוסבר למשתמש הסופי ישירות בעמוד ההורדה באתר.

## הרצת השרת (לתזמונים ולאפליקציית האנדרואיד)

צריך רק אם רוצים תזמונים/תזכורות (מהמחשב או מהטלפון). פיתוח מקומי:
```
npm run server:dev
```
רץ על http://localhost:3000 כברירת מחדל (`PORT` לשינוי). הוא גם מגיש את
`dist/` (האתר) וגם את ה-API תחת `/api/*` - בנייה אחת (`npm run build`)
לפני הרצתו בפרודקשן (`npm start`).

## פריסה אוטומטית ל-Node.js App בהוסטינגר (Git)

זה מה שנותן את העדכון האוטומטי: כל `git push` פורס לבד.

חשוב: בשלב "Build and output settings" בהוסטינגר יש רק שני שדות - **Package
manager** ו-**Entry file** - **אין** שדה נפרד ל-build command. לכן `dist/`
(פלט הבנייה של האתר) **מחויב ל-Git** בפרויקט הזה, ו-workflow של GitHub
Actions (`.github/workflows/build-dist.yml`) בונה אותו מחדש ומעדכן אותו
אוטומטית בכל push שמשנה קוד - כך שהשרת תמיד מקבל גרסה מוכנה בלי לבנות
בעצמו.

1. ב-hPanel: **Websites → [האתר שלך] → Node.js** (לא "Advanced → Git" הרגיל -
   זה מיועד לאתרים סטטיים בלי הבנה של Node כלל).
2. **Connect with GitHub**, בחרו את ה-repository ואת הענף לפריסה.
3. Root directory: `./` (ברירת המחדל - הפרויקט כולו בשורש ה-repo).
4. במסך "Change build and output settings":
   - **Package manager:** npm
   - **Entry file:** `server/index.js` - **לא** `electron/main.js` שממולא
     שם אוטומטית (זה קובץ ההפעלה של התוכנה להורדה, לא של השרת - אם משאירים
     אותו כך הפריסה תיכשל).
5. **Environment variables**:
   - `ELECTRON_SKIP_BINARY_DOWNLOAD=1` - מונע הורדת קובץ Electron הכבד בזמן
     ה-`npm install` בשרת - הוא בכלל לא נחוץ שם, רק בתוכנה להורדה שרצה אצלך.
   - `ALLOWED_SIGNUP_EMAILS` - **חובה כדי שמישהו יוכל בכלל ליצור חשבון**.
     רשימת מיילים מופרדת בפסיקים (לדוגמה: `me@example.com,partner@example.com`).
     ההרשמה סגורה - רק מיילים שברשימה הזו יכולים ליצור חשבון (ראו "חשבונות
     משתמש" למטה). זו בכוונה הגדרת סביבה בהוסטינגר ולא קובץ שנכנס ל-Git -
     הריפו ציבורי, ורשימת המיילים שלכם לא אמורה להופיע שם.
6. משאירים את `data/` (שם נשמר `db.json` עם החשבונות והתזמונים) - היא לא
   חלק מה-Git, אז עדכון קוד לא אמור למחוק אותה. מומלץ לוודא אחרי הפריסה
   הראשונה: תעשו שינוי קטן, דחפו שוב, ובדקו שהתזמונים לא נעלמו. אם כן
   נעלמו, יש להגדיר משתנה סביבה `DATA_DIR` לנתיב קבוע מחוץ לתיקיית הפרויקט.
7. אחרי הפריסה הראשונה, ב**תוכנה להורדה או באפליקציית האנדרואיד** (לא
   באתר הרגיל בדפדפן) → "תזמונים"/מסך החיבור → בוחרים "יצירת חשבון חדש",
   מזינים את כתובת השרת, מייל (חייב להיות ברשימת `ALLOWED_SIGNUP_EMAILS`)
   וסיסמה. מכאן והלאה מתחברים עם אותו מייל+סיסמה מ"התחברות לחשבון קיים".

## חשבונות משתמש

תזמונים (בתוכנה להורדה ובאפליקציית האנדרואיד) דורשים חשבון אישי - לא
סיסמת-על משותפת אחת. כל מי שנרשם רואה **רק את התזמונים שהוא עצמו יצר**,
גם אם כמה אנשים משתמשים באותו שרת.

- **הרשמה סגורה**: יוצרים חשבון רק עם מייל שנמצא ברשימת `ALLOWED_SIGNUP_EMAILS`
  שהגדרתם בהוסטינגר (משתנה סביבה, לא קובץ ב-Git - הריפו ציבורי, כך שרשימת
  המיילים שלכם לא נחשפת). מייל שלא ברשימה מקבל שגיאה ברורה ולא יכול
  להירשם, גם אם הוא מגיע ישירות ל-API.
- **מה קורה בפועל**: `POST /api/signup` (מייל+סיסמה, נבדק מול הרשימה)
  יוצר את החשבון; `POST /api/login` (אותו מייל+סיסמה) מחזיר טוקן חד-פעמי
  (לא שולחים את הסיסמה עצמה שוב בכל בקשה - היא נשלחת פעם אחת, בהתחברות
  בלבד) שנשמר מוצפן במכשיר (Keychain/DPAPI/libsecret ב-Electron,
  Android Keystore באפליקציה) ומשמש לכל קריאה מאומתת אחר כך.
- **בידוד נתונים אמיתי**: לכל תזמון יש `ownerId` בשרת, וכל ה-API (רשימה,
  יצירה, מחיקה, בדיקת "מה מגיע עכשיו") מסונן/מוגן לפי מי שמחובר - ניסיון
  לגשת לתזמון של מישהו אחר (גם עם ה-ID המדויק שלו) מחזיר "לא נמצא", לא
  שגיאת הרשאה שמאשרת שהתזמון קיים.
- **החלפת חשבון**: מזינים מייל+סיסמה אחרים ובוחרים "התחברות לחשבון קיים"
  (או "יצירת חשבון חדש" לחשבון שעוד לא קיים) - אין הגבלה על כמה חשבונות
  אפשר להתחבר איתם מאותו מכשיר, רק אחד בכל פעם.

## הרשאות USB בלינוקס (דפדפן או תוכנת ה-Desktop)

ב-Linux, גם דפדפן/Electron צריכים הרשאת מערכת הפעלה כדי לגשת ישירות
להתקן USB (לא משנה שזה WebUSB ולא `adb` נפרד - ההרשאה היא ברמת ה-USB
עצמו). ראו `deploy/51-android-usb.rules` בפרויקט הזה:

1. מצאו את ה-Vendor ID של הטלפון: `lsusb`
2. העתיקו את `deploy/51-android-usb.rules` ל-`/etc/udev/rules.d/`
   (ועדכנו בו את ה-Vendor ID אם צריך)
3. `sudo udevadm control --reload-rules && sudo udevadm trigger`
4. נתקו וחברו את הטלפון מחדש

## הרשאות USB ב-Windows

לפעמים ב-Windows הדרייבר שכבר מותקן לממשק ה-ADB "תופס" אותו ומונע
מ-Chrome/Electron לגשת אליו ישירות. אם לחיצה על "התחבר לטלפון" לא מציגה
את הטלפון ברשימה, יש להחליף את הדרייבר של ממשק ה-ADB (לא של כל הטלפון!)
ל-**WinUSB** בעזרת הכלי החינמי [Zadig](https://zadig.akeo.ie/).

## שימוש באפליקציה

הממשק בנוי כסיידבר עם 4 עמודים (חיבור הטלפון / אנשי קשר / הודעה ושליחה /
תזמונים) - עוברים ביניהם בלחיצה על הסיידבר, לא חייבים לעבור בסדר קבוע.
נקודה ירוקה ליד פריט בסיידבר מסמנת שהעמוד הזה כבר "מוכן" (טלפון מחובר,
קובץ נטען, הודעה נכתבה).

1. **חיבור הטלפון** - לחצו "התחבר לטלפון". יופיע חלון בחירת התקן של
   הדפדפן - בחרו את הטלפון. בפעם הראשונה תופיע בטלפון בקשת "לאפשר ניפוי
   USB?" - יש לאשר אותה פיזית על מסך הטלפון (אפשר לסמן "אפשר תמיד ממחשב
   זה" כדי לא לחזור על זה).
2. **אנשי קשר** - שתי דרכים למלא את הרשימה: להעלות קובץ `.xlsx`/`.xls`/`.csv`
   (כל עמודה בקובץ - לדוגמה "שם", "טלפון", "עיר", "סכום" - הופכת אוטומטית
   לפרמטר זמין), או **לייבא מקבוצות וואטסאפ** - ראו פרק ייעודי למטה. בשתי
   הדרכים בוחרים בסוף איזו עמודה היא מספר הטלפון ואיזו היא השם (המערכת
   מנסה לנחש את שתיהן). בעמוד הזה אפשר גם **לשמור את כולם כאנשי קשר
   בטלפון** - ראו פרק ייעודי למטה.
3. **הודעה ושליחה** - כתבו את ההודעה, ולחצו על צ'יפים כמו `{שם}` כדי
   להוסיף פרמטר מכל עמודה בקובץ במקום הסמן. מתחת לתיבת הטקסט מופיעה
   תצוגה מקדימה - טבלה שמראה בדיוק מה יישלח לכל איש קשר (עד 20 שורות
   ראשונות), כולל אזהרה על פרמטר שלא קיים בקובץ (טעות הקלדה למשל).
   למטה בוחרים ערוץ (SMS או WhatsApp - ראו פרק ייעודי למטה). "מצב בדיקה"
   מסומן כברירת מחדל ומדמה את התהליך בלי לשלוח באמת. מבטלים את הסימון
   כדי לשלוח בפועל. יש הגבלת קצב (השהיה בין הודעות) כדי לא להעמיס על
   הטלפון ולא להיראות כספאם. חשוב שהמסך של הטלפון יישאר **דלוק ולא
   נעול** לאורך כל השליחה - נעילת מסך היא שכבת אבטחה נפרדת מהרשאת ה-USB,
   ו-Android לא מאפשר לדמות הקשות על מסך נעול (בכוונה - זו הגנה, לא
   תקלה).
4. **תזמונים** (בתוכנה להורדה בלבד, מופיע בסיידבר רק אז) - אחרי שמתחברים
   לחשבון פעם אחת (ראו "חשבונות משתמש" למטה), טוענים קובץ אנשי קשר וכותבים
   הודעה כרגיל (עמודים
   2-3), ואז בעמוד "תזמונים" בוחרים תווית ותדירות (חד פעמי / כל יום /
   כל שבוע) ולוחצים "צור תזמון". התוכנה שומרת את הרשימה וההודעה מקומית
   במחשב הזה, ורצה ברקע (גם כשהחלון סגור - יש סמל במגש המערכת) כדי לבדוק
   מול השרת ולשלוח בזמן.

## ייבוא אנשי קשר מקבוצות וואטסאפ

בעמוד "אנשי קשר" יש כפתור "טען קבוצות מהטלפון" - הוא פותח את וואטסאפ
בטלפון (דרך אותו חיבור USB), עובר לפילטר "קבוצות" בראש רשימת הצ'אטים,
וגולל אותה כדי לאסוף את שמות כל הקבוצות. לאחר מכן בוחרים אילו קבוצות
רלוונטיות, ולוחצים "בנה אנשי קשר מהקבוצות שנבחרו" - המערכת נכנסת לכל
קבוצה שנבחרה, פותחת את "פרטי הקבוצה" וקוראת את רשימת החברים (שם + מספר
טלפון) ישירות מהמסך. התוצאה הופכת לרשימת אנשי קשר לכל דבר - **בדיוק
כאילו הועלה קובץ** - כולל עמודת "קבוצה" נוספת שאפשר להשתמש בה כפרמטר
בהודעה, וממשיכה לזרום לתצוגה המקדימה, לשליחה, ולשמירה כאנשי קשר בטלפון.

- **אין API רשמי לזה** - חשבון וואטסאפ אישי (לא Business API) לא חושף
  שום דרך תכנותית למשוך קבוצות/חברים. השיטה היחידה היא לקרוא את המסך של
  וואטסאפ עצמו - בדיוק כמו איתור כפתור "שלח" בשליחת הודעות, רק על כמה
  מסכים ברצף (רשימת קבוצות, מסך הקבוצה, פרטי הקבוצה) במקום מסך אחד.
- **זה הפיצ'ר הכי שביר במערכת, ובכוונה** - כשביקשת את הפיצ'ר הזה, נבחרה
  במפורש הגישה הזו (חיבור USB קיים) על פני חיבור ישיר לוואטסאפ מסוג
  WhatsApp Web/Desktop (סריקת QR), כי החלופה עובדת רק בתוכנת ה-Desktop
  ומשתמשת בפרוטוקול לא רשמי עם סיכון חסימה. המחיר: זיהוי הקבוצות
  והחברים מבוסס על ניחושים לגבי מבנה המסך של וואטסאפ (למשל: פילטר בשם
  "Groups"/"קבוצות" בראש רשימת הצ'אטים, ומספר טלפון שמופיע כטקסט ליד כל
  חבר קבוצה) שנבדקו רק מול קבצי דמה שנבנו ידנית - **לא מול מכשיר אמיתי**.
  אם עדכון עתידי של וואטסאפ ישנה את המסכים האלה, הפיצ'ר עלול להפסיק
  לעבוד עד לעדכון בקוד.
- כל קבוצה נטענת בנפרד, כך שכישלון בקבוצה אחת (למשל שינתה שם, או
  שהמכשיר ננעל באמצע) לא עוצר את שאר הקבוצות שנבחרו - טבלת התוצאות מראה
  סטטוס נפרד לכל קבוצה.
- חברים עם אותו מספר טלפון בכמה קבוצות שנבחרו יחד מופיעים פעם אחת בלבד
  ברשימה הסופית.

## שמירת אנשי קשר בטלפון

בעמוד "אנשי קשר", אחרי טעינת הקובץ, אפשר ליצור איש קשר חדש בטלפון לכל
שורה - שימושי כדי שהנמענים יראו את השם שלכם (או שם עסק) על הצג במקום
מספר לא מזוהה, לפני ששולחים להם הודעה.

- **בלי כפילויות** - לפני היצירה המערכת שולפת מהטלפון (דרך `content
  query` על ה-Contacts Provider, ללא צורך באפליקציה נלווית) את כל
  המספרים שכבר שמורים, ומדלגת אוטומטית על מי שכבר קיים (לפי מספר טלפון
  מנורמל - בלי רגישות לרווחים/מקפים/פורמט). זה גם עובד בתוך הקובץ עצמו:
  אם אותו מספר מופיע פעמיים בקובץ, רק הפעם הראשונה תיצור איש קשר.
- **מנגנון האיתור זהה לשליחת ההודעות** - נפתח מסך "יצירת איש קשר" הרגיל
  של אנדרואיד עם השם והמספר ממולאים, ואז המערכת מאתרת ולוחצת על כפתור
  "שמור"/"סיום" אוטומטית (יש גם "מצב בדיקה" נפרד לפיצ'ר הזה, ושדה
  קואורדינטות גיבוי ידניות בתוך הפיצ'ר עצמו למקרה שהאיתור האוטומטי נכשל).
- טבלת התוצאות מראה לכל שורה אם איש הקשר **נוצר**, **דולג** (כבר היה
  שמור), או **נכשל** (למשל מספר חסר/לא תקין).

## שליחה דרך WhatsApp

אותו מנגנון בדיוק כמו SMS (פתיחת מסך כתיבה עם ההודעה ממולאת, איתור
ולחיצה על "שלח") - רק שנפתח דרך קישור ה-"click to chat" הרשמי של
WhatsApp במקום אפליקציית ה-SMS.

- **פורמט המספר שונה מ-SMS**: WhatsApp דורש פורמט בינלאומי מלא (למשל
  `972501234567`), לא פורמט מקומי (`0501234567`). כשבוחרים בערוץ
  WhatsApp מופיע שדה "קידומת מדינה" (ברירת מחדל `972` - ישראל) -
  מספרים שמתחילים ב-`0` בקובץ יומרו אוטומטית, מספרים שכבר בפורמט
  בינלאומי יישארו כפי שהם.
- **קידומת לפי איש קשר (רשימות מעורבות)**: אם ברשימה יש גם מספרים
  ישראליים וגם זרים שכולם כותבים אותם עם `0` מוביל (נפוץ במדינות
  רבות), קידומת גלובלית אחת לא מספיקה. אפשר להוסיף עמודה בקובץ עצמו
  (למשל "קידומת מדינה") עם קידומת שונה לכל איש קשר - המערכת מזהה
  עמודה כזו אוטומטית (או בוחרים ידנית מהתפריט), ומשתמשת בערך שלה
  **לאותה שורה בלבד** במקום בברירת המחדל הגלובלית. שורה בלי ערך בעמודה
  הזו פשוט מקבלת את ברירת המחדל כרגיל.
- **שני הערוצים יחד** - בוחרים "שניהם" כדי לשלוח גם SMS וגם WhatsApp
  לכל איש קשר (שתי הודעות נפרדות, כל אחת עם המספר בפורמט המתאים לה
  - טבלת התוצאות מציגה עמודת "ערוץ" כדי להבדיל ביניהן).
- **אין דרך לבדוק "יש לאיש קשר WhatsApp?" מראש** - אין API רשמי לכך בלי
  WhatsApp Business API (אישור עסקי נפרד מ-Meta, לא רלוונטי לחשבון
  אישי). ניסיון פתיחת הצ'אט **הוא** הבדיקה - אם למספר אין WhatsApp,
  זה יופיע כ"נכשל" באותו איש קשר (בלי לעצור את השאר), לרוב עם הסבר
  שמזכיר את זה בהודעת השגיאה.
- **סיכון חסימה - חשוב לקרוא**: שליחה המונית מחשבון WhatsApp אישי (לא
  Business API רשמי) יכולה לגרום לחסימה זמנית או קבועה של המספר, בעיקר
  בכמויות גדולות או לנמענים שלא שמרו אתכם כאיש קשר. המערכת עוזרת
  בכמה דברים (השהיה ברירת מחדל ארוכה יותר לוואטסאפ - 20 שניות במקום 4,
  עם אקראיות רחבה יותר סביב כל השהיה, ומדי פעם - בערך פעם ב-12
  הודעות - הפסקה ארוכה בהרבה שמדמה מישהו שהתרחק לרגע מהטלפון), אבל **זה
  מקטין סיכון, לא מבטל אותו**. מומלץ להתחיל בכמות קטנה ולעקוב אחרי
  התוצאות לפני שליחה לרשימה גדולה.

## שליחה עצמאית מהטלפון (אפליקציית Android)

מקביל לכל מה שיש עד כה: אפליקציית אנדרואיד עצמאית (`android/`, פרויקט
Kotlin/Gradle נפרד) שמתקינים ישירות על הטלפון, מתחברת לאותו שרת קטן, ושולחת
SMS **בעצמה** ברקע - בלי חיבור USB למחשב בזמן השליחה, ובלי שהמחשב יהיה
דלוק בכלל.

- **שינוי מהותי בפרטיות, ובכוונה**: בכל מקום אחר במערכת (כולל תזמון
  "מהמחשב") השרת אף פעם לא רואה רשימת אנשי קשר או תוכן הודעה - רק
  "מתי להריץ". תזמון "מהטלפון" הוא היוצא מן הכלל המפורש: כדי שהטלפון יוכל
  למשוך תוכן בלי מחשב מעורב, ה-payload (`rows`/`template`/`phoneColumn`)
  **כן** נשמר בשרת (`server/db.js`, שדה `payload` על התזמון). זה טרייד-אוף
  מודע שאושר מראש - לא ברירת מחדל סמויה. ראו את התיעוד בראש `server/index.js`.
- **SMS בלבד** - לאפליקציה יש גישה ל-API הרשמי של אנדרואיד לשליחת SMS
  (`SmsManager`), הרבה יותר אמין מסימולציית הקשות. לוואטסאפ אין API רשמי
  גם כאן, ולכן וואטסאפ עצמאי מהטלפון לא נתמך (אפשר עדיין לשלוח וואטסאפ
  דרך תזמון "מהמחשב" הרגיל, שרץ עם הטלפון מחובר ל-USB).
- **ארכיטקטורה**: `MainActivity` מתחברת לשרת עם חשבון אישי (מייל+סיסמה,
  אותו מנגנון כמו האתר/התוכנה - ראו "חשבונות משתמש" למעלה) ומבקשת הרשאת
  שליחת SMS; `SyncWorker` (WorkManager,
  כל 15 דקות - המרווח המינימלי המובטח של אנדרואיד לעבודות תקופתיות ברקע)
  שואל את השרת `GET /api/schedules/due?runMode=phone`, שולח הודעה לכל
  שורה (עם אותה לוגיקת `{פרמטר}` בדיוק כמו `templating.js`, מיושמת מחדש
  ב-Kotlin ב-`Template.kt`), ומדווח בחזרה דרך `POST /api/schedules/:id/ack`
  - אותו endpoint בדיוק שהתוכנה להורדה כבר משתמשת בו.
- **שני מצבי עבודה, לבחירה במסך ההגדרות שבאפליקציה**:
  - **אוטומטי (ברירת המחדל)** - בדיוק כמו שתואר למעלה: התחברות רושמת גם
    בדיקה מיידית וגם `SyncWorker` תקופתי (כל 15 דקות), הכול קורה ברקע בלי
    מעורבות נוספת.
  - **ידני** - כשמכבים את המתג "סנכרון אוטומטי ברקע" בהגדרות, שום דבר לא
    נשלח לבד. במקום זה, במסך הבית מסמנים (checkbox) בדיוק אילו תזמונים
    "מהטלפון" רוצים להריץ עכשיו (לא רק את מה שה"תזמון" עצמו מגדיר כ"הגיע
    הזמן" - הבחירה היא של המשתמש, לא של הטיימר), לוחצים "משוך את התזמונים
    הנבחרים" (קריאה חד-פעמית ל-`GET /api/schedules/:id` החדש שמחזיר את
    ה-payload המלא של תזמון ספציפי; השרת עצמו שומר על אותה מדיניות הרשאות
    כמו כל שאר ה-API), הנתונים נשמרים מקומית בטלפון
    (`LocalCache`, אחסון פנימי רגיל של האפליקציה, לא מוצפן כמו פרטי
    ההתחברות כי זה מידע עבודה זמני ולא אישורי גישה) ונשארים שם גם אם סוגרים וחוזרים
    לאפליקציה. לוחצים "שלח את מה שנמשך עכשיו" והשליחה עצמה רצה מיד בחזית
    האפליקציה (לא דרך `WorkManager`/`SyncWorker` - במצב הזה המשתמש צופה
    בתהליך במקום שהוא קורה מאחורי הקלעים), עם עדכון התקדמות חי ("שולח X
    מתוך Y"). בסיום נפתח מסך "דו״ח שליחה" שמפרט **לכל איש קשר בנפרד** אם
    נשלח בהצלחה או נכשל (ולמה) - דו"ח שקיים רק על הטלפון עצמו, לא נשמר
    בשרת.
- **מנגנון עדכון גרסה, כולל פוש**: כדי שגרסה חדשה שה-CI מפרסם *תגיע*
  בפועל לטלפון בלי שהמשתמש יזכור לחזור לאתר ולהוריד שוב:
  - כל בנייה ב-CI מקבלת `versionCode` שתמיד עולה (`GITHUB_RUN_NUMBER` -
    מספר ריצת ה-workflow, אף פעם לא חוזר אחורה), ומפרסם גם `android-version.json`
    קטן לאותו GitHub Release (אותה שיטת URL יציב/עמיד-לתגית כמו שאר קבצי
    ההורדה).
  - **רשת ביטחון תקופתית, עובדת מהקופסה בלי שום הגדרה**: `UpdateCheckWorker`
    (WorkManager, כל 12 שעות) קורא את `android-version.json`, משווה מול
    `BuildConfig.VERSION_CODE` של האפליקציה המותקנת, ואם יש גרסה חדשה - מוריד
    את ה-APK ברקע (`UpdateDownloader`) ומציג התראה; לחיצה עליה פותחת את מסך
    ההתקנה של אנדרואיד (`FileProvider` + `ACTION_VIEW`, דורש הרשאת
    `REQUEST_INSTALL_PACKAGES`) - "לחיצה אחת להתקנה", לא התקנה שקטה לגמרי
    (אנדרואיד תמיד דורש אישור סופי להתקנת APK מחוץ לחנות, גם לעדכון אפליקציה
    שכבר מותקנת). יש גם כפתור "בדוק עדכונים עכשיו" ידני במסך ההגדרות.
  - **פוש אמיתי דרך Firebase, מיידי במקום להמתין עד 12 שעות**:
    `UpdatePushService` (`FirebaseMessagingService`) מאזין לנושא (topic)
    בשם `app-updates` שהאפליקציה נרשמת אליו אוטומטית בהפעלה ראשונה. ה-CI
    (אחרי פרסום ה-APK) שולח הודעת push ריקה-מתוכן (data-only, לא
    notification - כדי שתפעיל קוד גם כשהאפליקציה סגורה) לנושא הזה. ה-push
    לא נסמך על תוכן שהגיע מבחוץ - הוא רק "טריגר לבדיקה מיידית" שמריץ מיד
    את אותו `UpdateCheckWorker`, כדי לא לשכפל לוגיקה.
  - **הגדרה חד-פעמית שרק אתם יכולים לעשות** (אני לא יכול ליצור פרויקט
    Firebase או מפתחות בעצמי - זה דורש חשבון גוגל אישי):
    1. [console.firebase.google.com](https://console.firebase.google.com) →
       פרויקט חדש (כל שם) → הוספת אפליקציית Android עם החבילה
       `com.smsclicksender.app` → הורדת `google-services.json`, והחלפה איתו
       של `android/app/google-services.json` שבריפו (שם כרגע קובץ placeholder
       עם ערכים מזויפים - קובץ כזה בטוח לגמרי לשמור בקוד, בדיוק כמו בגרסה
       האמיתית - הוא ממילא ארוז בתוך כל APK שמופץ, כך גוגל עצמה ממליצה).
    2. Firebase Console → Project Settings → Service Accounts → Generate
       new private key → מוריד קובץ JSON. הוסיפו אותו כ-secret בריפו:
       Settings → Secrets and variables → Actions → New repository secret,
       שם `FCM_SERVICE_ACCOUNT_KEY`, ערך = **כל תוכן** קובץ ה-JSON. **לעולם
       לא לשמור את הקובץ הזה בתוך הקוד עצמו** - הוא נותן הרשאת שליחה מלאה
       לפרויקט.
    עד שזה לא מוגדר, ה-CI פשוט מדלג על שלב שליחת ה-push (בלי להיכשל, ראו
    `android/ci/send-update-push.mjs`), והאפליקציה ממשיכה לעבוד עם רשת
    הביטחון התקופתית בלבד.
- **בנייה/פיתוח**: `cd android && ./gradlew assembleDebug` (או
  `./gradlew test` להרצת הבדיקות של `Template.kt`). ה-CI
  (`.github/workflows/build-android-app.yml`) בונה APK debug (לא חתום -
  אין חנות Play שדורשת חתימת release, וגם ממילא מדיניות ה-SMS של Google
  Play לא הייתה מאשרת אפליקציה כזו שם) ומפרסם אותו לאותו GitHub Release
  שהתוכנות למחשב משתמשות בו.
- **מגבלת בדיקה אמיתית וחשובה**: בסביבת הפיתוח הזו **אין** גישת רשת
  ל-Android SDK/Maven של גוגל (חסום ברמת מדיניות הרשת) - כך שבשונה מכל
  שאר הפרויקט, קוד ה-Kotlin **לא נבדק ולו פעם אחת** על ידי בנייה מקומית
  מלאה לפני שנדחף; האימות היחיד הוא ה-CI (שרץ על ריצות GitHub-hosted, שכן
  יש להן גישת רשת מלאה לגוגל - בשונה מהסביבה הזו). כן הצלחתי לוודא בפועל
  (קימפול+הרצה ישירה מול ה-Kotlin compiler, בלי Android SDK, כולל
  `org.json`/OkHttp האמיתיים שהורדו מ-Maven Central - לא רק ה"stub" הריק
  שיש בתוך ה-Android SDK) שהלוגיקה הטהורה עובדת נכון: `Template.render`/
  `normalizePhone` תואמים בדיוק ל-JS המקביל להם (מכוסה גם ב-
  `android/app/src/test/kotlin`), `LocalCache` ומנגנון קידוד/פענוח דו"ח
  השליחה עברו בדיקת round-trip אמיתית, ו-`UpdateChecker`/`UpdateDownloader`
  (בדיקת/הורדת עדכון) עברו בדיקה אמיתית מול שרת HTTP מקומי - כולל טקסט
  בעברית בכל המקרים. גם סקריפט שליחת ה-push (`send-update-push.mjs`) הורץ
  בפועל עם מפתח שירות מזויף (אבל תקין מבחינת המבנה) - הבקשה הגיעה בפועל
  לשרתי האימות של גוגל וקיבלה שגיאת "invalid_grant" צפויה (כי החשבון לא
  קיים), מה שמאשר שהלוגיקה נכונה עד לנקודה שרק מפתח אמיתי יכול לעבור אותה.
  שאר הקוד שנוגע ישירות ב-Android APIs (מסכים/Activities, WorkManager,
  SmsManager, Firebase Messaging עצמו, העיצוב) נכתב בקפידה אבל טרם עבר
  בדיקה אמיתית על מכשיר.

## מגבלות ידועות

- **רק דפדפנים מבוססי Chromium** (ולא בדפדפן נייד בכלל - זה פיצ'ר Desktop).
- שיטת "סימולציית ההקשה" תלויה במסך שהמכשיר לא נעול. אם המכשיר ננעל
  באמצע ריצה, ההודעות הבאות לא יישלחו (יופיע כישלון בטבלת התוצאות).
- אפליקציות SMS שונות (Google Messages, Samsung Messages וכו') עלולות
  להיראות שונה על המסך; יש שדה "קואורדינטות גיבוי ידניות" בהגדרות
  המתקדמות למקרה שהאיתור האוטומטי נכשל על מכשיר/אפליקציה מסוימת.
- חבילת `xlsx` (SheetJS) שבה משתמשים לקריאת הקבצים מסומנת ע"י `npm audit`
  עם חשיפת אבטחה ידועה (ללא תיקון זמין ב-npm) שרלוונטית בעיקר לפענוח
  קבצים ממקור לא מהימן על שרת משותף. כאן זה לא רלוונטי בפועל: זה קורה
  אך ורק בדפדפן שלך, על קובץ שאתה עצמך בחרת מהמחשב שלך.
- אין הגבלה חוקית/רגולטורית מובנית (כמו הסכמת נמען, שעות שליחה מותרות
  וכו') - האחריות על תוכן ואופן השימוש היא על המשתמש.
- **תזמונים** דורשים שהתוכנה להורדה תישאר פתוחה (גם אם ממוזערת/במגש
  המערכת) על מחשב שהטלפון מחובר אליו, והמחשב לא יירדם/יכבה. התזמון נבדק
  כל דקה בערך - אז "9:00 בדיוק" עשוי לצאת בפועל 9:00-9:01. אם המחשב היה
  כבוי/ישן בזמן שהתזמון היה אמור לרוץ, הוא ירוץ בפעם הראשונה שהתוכנה
  שוב בודקת מול השרת ורואה שהזמן כבר עבר - לא ידלג עליו, אבל גם לא ירוץ
  "בזמן".
- תזמון שנוצר במחשב אחד לא "רואה" אותו מחשב אחר - כל תזמון קשור לרשימת
  אנשי הקשר/הודעה שנשמרו מקומית איפה שהוא נוצר.
